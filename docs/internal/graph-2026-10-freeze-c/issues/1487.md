## Problem

`sequant run` finds an issue's existing worktree by a branch name rebuilt from the issue title. If the title differs from the one the branch was cut with, it misses the branch and creates a second one from the base:
- `ensureWorktree` builds `feature/${issueNumber}-${slugify(title)}` (`src/lib/workflow/worktree-manager.ts:987-988`).
- It looks that exact name up (`findExistingWorktree(branch)`, `:148`, a substring match on `git worktree list --porcelain`).

Two triggers:
1. **A failed `gh issue view`.** `getIssueInfo` (`src/lib/workflow/batch-executor.ts:318-351`) returns the title `Issue #N` for every `gh` failure except "Could not resolve to an issue" (offline, auth, rate limit, 5xx, unparseable JSON). This is the silent default #1257 kept on purpose. The orchestrator passes it straight to `ensureWorktree` (`run-orchestrator.ts:1161-1163`, `:1294`).
2. **A retitled issue.** Any title edit after the branch exists changes the slug.

Then:
- The phase runs in a fresh worktree at the base.
- `batch-executor.ts:1164-1170` overwrites state.json's `branch`/`worktree` record with the new branch.
- `sequant worktree resolve N` now reports `WORKTREE_AMBIGUOUS`.

**Seen:** 2026-10-16, a qa-only re-run of #1305 (MCP `sequant_run`, phases `qa`) whose `gh issue view` failed. It created `feature/1305-issue-1305` from `main` next to the PR branch `feature/1305-fix-qa-a-sequant-mutation-marker-whose-text-contai`, and QA recorded `commit: null`.

**Reproduced** on `main` (085748480), in a temp clone using the #1380 harness shape:
1. `ensureWorktree(1305, "fix(qa): a SEQUANT_MUTATION marker whose text contains }")`, then a commit pushed with `-u`.
2. `ensureWorktree(1305, "Issue #1305")` returned `{ branch: "feature/1305-issue-1305", existed: false }`, at the `init` commit. The PR worktree still held `pr commit`.

Everything else in `src` already treats the issue number as a branch's identity:
- `listWorktrees` (parses `issue` from the branch) and `resolveIssueWorktree` (`worktree-resolver.ts:67`, #899/#900)
- `parseIssueNumberFromBranch` (`worktree-discovery.ts:75`)
- `merge-check/index.ts:143` (`^feature/${n}-`)
- `pr-status.ts:132`

Only the code that creates worktrees keys on the title.

## Acceptance Criteria

- [ ] AC-1: When exactly one branch for issue N exists (a worktree of this repo, a local `refs/heads/feature/N-*`, or `refs/remotes/origin/feature/N-*`), `ensureWorktree` reuses that branch whatever title it is given, including the fallback `Issue #N` and a changed title, and creates no new branch. Evidence: `npx vitest run src/lib/workflow/worktree-manager.test.ts -t "reuses the issue's branch"` reports ≥ 4 passed, 0 failed. The temp-repo tests cover (a) an existing pushed worktree called again with title `Issue #N`, (b) the same with a different real title, and (c) a fresh clone where only `origin/feature/N-<slug>` exists, called with title `Issue #N`, and (d) issue 1 beside an existing `feature/12-other` branch, which must not be taken as issue 1's branch (the prefix match includes the dash). Each asserts the returned branch equals the original and `git branch --list 'feature/N-issue-n'` is empty. Mutation-verified by restoring the title-only lookup (`findExistingWorktree(\`feature/${issueNumber}-${slug}\`)`).
- [ ] AC-2: When two or more branches for issue N exist, `ensureWorktree` creates no new branch. It uses the one whose name equals the title-derived name if there is one. Otherwise it returns no worktree and prints every candidate branch, and the issue fails rather than running in another checkout. Evidence: `npx vitest run src/lib/workflow/worktree-manager.test.ts -t "several branches for one issue"` reports ≥ 1 passed, 0 failed: a temp-repo test with `feature/N-a` and `feature/N-b` and title `Issue #N` asserting no third branch, a null result and both names in the output; mutation-verified by making the multi-match case pick the first candidate.
- [ ] AC-3: A non-dry run that could not read an issue's title (a `gh` failure other than not-found) prints a warning naming the issue and the `gh` error before worktree setup. A run that read the title prints no such warning. Evidence: `npx vitest run src/lib/workflow/get-issue-info.test.ts -t "title unreadable warning"` reports ≥ 2 passed, 0 failed: a test that stubs `spawnSync` to fail with `HTTP 502` and asserts the warning names `#N`, plus a passing-`gh` case that asserts no warning; mutation-verified by removing the warning.
- [ ] AC-4: With no branch for issue N anywhere, first creation is unchanged: `feature/N-<slugify(title)>` from the run's base, or from `origin/<branch>` on a fresh machine (#1405). Evidence: `npx vitest run src/lib/workflow/worktree-manager.test.ts -t "1380|1405"` reports 0 failed, with no test edited.

- **Consumers that key on the issue number:** `resolveIssueWorktree`, `listWorktrees`, `worktree-discovery`, `merge-check`, `pr-status`, `checkout-lock.ts:182`, `cleanup-worktree.sh`.
- The ACs state the outcome (one branch per issue is reused whatever the title) rather than patching the fallback title, so the gh blip and the retitle are both closed.
- **Source of truth:** a git ref for the issue number, because it is local, needs no network and is present on a fresh machine once fetched. Not state.json, whose `branch` record is per-checkout and is overwritten by the stray branch (`batch-executor.ts:1166`). Not the PR's `headRefName`, which needs the `gh` call that just failed.
