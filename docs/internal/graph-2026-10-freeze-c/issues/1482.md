## Problem

A repo adopted with `init --manifest-only` + `sync --only skills` records `groups: ["skills"]` in `.sequant-manifest.json` (#1409, ADR-0015). Bare `sequant update` ignores that scope:
- It computes the whole template set (`src/commands/update.ts:213` `newFiles`, `:252` `applySet`).
- It writes every new file, including `.claude/hooks/`, the agents and `.claude/settings.json`.

Since #1477, the manifest then records a full install. The record is now true, but the scope the user chose is widened without a prompt.

`update` is the documented upgrade command, and some remedy text still points scoped installs at it. So a skills-only adopter who upgrades the normal way gets hooks and a `settings.json` they opted out of.

## Not the #1409 Non-Goal

#1409 excluded an `update --only` **flag**. This issue is about `update` reading the scope the manifest **already records**. It adds no new flag.

## Decision (owner, 2026-10-16): option B

On a partial scope, `update` stops and names the scoped upgrade command, `sync --only skills`. It writes nothing.

`sync --only skills` already upgrades a scoped install. I checked on 2026-10-16 in a temp repo: with `.claude/skills/.sequant-version` set to `0.0.1` and a stale skill, it rewrote the skill, reset the marker, kept `groups: ["skills"]`, and wrote nothing outside `.claude/skills/`. So `update` needs no second scope filter. It reads the scope through `getInstallScope` and refuses.

Rejected:
- **A:** filter `update`'s change set to the scope. That makes a second apply path for a partial install.
- **C:** keep `update` as the "widen to full" command and only fix the remedy text. That leaves the documented upgrade command widening a scoped install without a prompt.

ADR-0015 must be amended. #1477 wrote "`update` installs every group, so it removes the field too". That stays true only for a full install. On a partial scope, `update` now refuses.

## Acceptance Criteria

- [ ] AC-1: On a manifest with `groups: ["skills"]`, `update` (with `--yes`, and with `--force`) writes no file (the `.mcp.json` pin included), leaves the manifest byte-identical, sets a non-zero exit code, and prints the scoped upgrade command `sync --only skills`. Evidence: `npx vitest run src/commands/sync.install-scope.integration.test.ts -t "update refuses on a skills-only install"` reports ≥ 1 passed, 0 failed, mutation-verified by deleting the partial-scope check in `src/commands/update.ts` (exactly those tests fail).
- [ ] AC-2: On a manifest with `groups: ["skills"]`, `update --dry-run` prints the same message, writes nothing and sets a non-zero exit code. Evidence: `npx vitest run src/commands/sync.install-scope.integration.test.ts -t "update --dry-run refuses on a skills-only install"` reports ≥ 1 passed, 0 failed.
- [ ] AC-3: On a manifest without `groups` (full install), `update` behaves exactly as today: it applies all new and modified files and writes no `groups` field. Evidence: `npx vitest run src/commands/update.test.ts src/commands/update.integration.test.ts` reports 0 failed, and `npx vitest run src/commands/sync.install-scope.integration.test.ts -t "update on a full install"` reports ≥ 1 passed.
- [ ] AC-4: ADR-0015 and the Updating section of `docs/getting-started/installation.md` say that `update` refuses on a partial scope and that `sync --only skills` upgrades a skills-only install. Evidence: `sed -n '/^## Updating/,/^## Directory/p' docs/getting-started/installation.md | grep -c "sync --only skills"` prints ≥ 1 (0 today), and `grep -c "installs every group, so it removes the field too" docs/adr/0015-install-scope-recorded-in-manifest.md` prints 0.

## Prior fixes / producers

- Prior fixes on `update`'s manifest write: #1409 (PR #1467) added `groups`; #1477 (2026-10-16) made `update` record a full install. This issue replaces #1477's behaviour on a partial scope. #1477's test `an update on a skills-only install records a full install` (`sync.install-scope.integration.test.ts`) asserts the old behaviour and is rewritten to AC-1's.
- Commands that write templates over a scoped install: `update` (this issue), `sync --only skills` (keeps the scope), and plain `sync` at a version mismatch (widens to full, recorded by #1409's test `a full sync on a skills-only install records a full install`). Plain `sync` is node A's (graph-2026-10-freeze-c). This issue is deliberately local to `update`: B is a refusal, not a second scope filter, and the scope is read through `getInstallScope` (`src/lib/manifest.ts:74`), the one reader.
