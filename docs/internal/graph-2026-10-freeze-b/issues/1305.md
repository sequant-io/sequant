**Found:** 2026-10-04, runner of #1289 (PR #1303). A hand-written mutation marker whose `mutation` text contained a regex quantifier (`/\$[0-9]{9}/`) parsed to `[]`.

**Problem.** `MUTATION_MARKER_REGEX` (`src/lib/workflow/mutation-marker.ts:28`) is `/<!-- SEQUANT_MUTATION: (\{[^}]+\}) -->/g`. It stops the JSON at the first `}`. So any field containing `}` makes the marker disappear silently, and that is common in a `mutation` description of a regex or code change. `renderMutationMarker` is documented as "the inverse of the parser", but it isn't:

```
renderMutationMarker({ac:"AC-2", mutation:"regex changed to /x{9}/", failedTest:"a.test.ts > d > c"})
  → <!-- SEQUANT_MUTATION: {"ac":"AC-2","mutation":"regex changed to /x{9}/",…} -->
parseMutationMarkers(that)               → []
parseMutationMarkersFromExecOutput(that) → []
```

The failure is silent at both ends. #1297's carry-over drops the marker, so the PR body has no marker. §6i then reads the gate-test AC as unrecorded and floors the verdict, even though exec did the mutation work.

**Freeze check (2026-10-16):** `/qa` §6i calls `parseMutationMarkers` through `npx tsx`; it doesn't embed the regex. The fix needs no skill edit.
