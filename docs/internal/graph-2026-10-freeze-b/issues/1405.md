Follow-up from #1380 (PR #1403; spec Open Question 2 and a QA `document` finding).

## Problem

#1380 makes a **stale-worktree recreate** start from `origin/<branch>`. Two neighbouring paths still lose or repeat work:

1. **Fresh machine, first creation.** With no local branch but an existing `origin/<branch>` (a PR opened from another machine, or a cloud session), `ensureWorktree` still checks the branch with the local-only `show-ref refs/heads/<branch>` (`worktree-manager.ts:1078`). It falls through to `git worktree add <path> -b <branch> <baseRef>`, a new branch cut from the base. A qa re-run there reviews the base, and a later push diverges from the PR. That's #1380's bug, on the first-creation path.
2. **A recreated worktree stays stale.** Recreating from `origin/<branch>` keeps the PR's commits, but the branch is still more than 5 commits behind the base. So every later `ensureWorktree` call recreates it again (delete, re-add, dependency reinstall) until the pre-PR rebase or a merge of the base lands.

## Design constraint (graph doc §6, OQ-2)

AC-3's "abandoned branch" check must not add a network call to every `ensureWorktree`. #1322's root cause was real `git worktree list` + `gh` calls per worktree, which made run time scale with load. The spec answers where the check runs (first-creation and recreate paths only) and whether a local `git` check is enough (for example, `origin/<branch>` already contained in `origin/<base>`).

## Acceptance Criteria

- [ ] AC-1: With no local `<branch>` and an existing `origin/<branch>`, `ensureWorktree` creates the worktree from `origin/<branch>` with upstream tracking, so HEAD contains every commit of `origin/<branch>`. Evidence: a temp-repo test in `worktree-manager.test.ts` (the #1380 harness), mutation-verified by restoring the `-b <branch> <baseRef>` path.
- [ ] AC-2: A worktree recreated from `origin/<branch>` is not recreated again by the next `ensureWorktree` call when nothing changed on `origin/<branch>`. Either the base is merged in at recreate time, or the staleness check skips a branch whose HEAD equals `origin/<branch>`. Evidence: a test calling `ensureWorktree` twice, asserting the second call reuses the worktree.
- [ ] AC-3: A remote branch already merged into the base is not resurrected as the new work's base, and the check adds no `gh` call on the reuse path. Evidence: a test covering a branch already merged into `origin/<base>`, plus a test asserting the reuse path makes no `gh` call.
