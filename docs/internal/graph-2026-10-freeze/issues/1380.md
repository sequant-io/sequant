## Summary

When a PR's worktree is more than 5 commits behind base and has no uncommitted or unpushed work, `ensureWorktree` "recreates fresh". In doing so it deletes the local branch and rebuilds it **from base**, ignoring `origin/<branch>`. A qa re-run then reviews base with none of the PR's commits.

## Observed

the reporting downstream repo, 2026-10-06, sequant 2.19.0 over MCP. On a qa re-run the log printed `Worktree is 12 commits behind master — recreating fresh`. QA then recorded `"commit": null` and `filesModified: []`. The worktree had none of the PR's commits; `git log origin/master..HEAD` was empty. The QA agent happened to notice and ran `git show <head>:<file>` itself, but nothing in sequant guards against this.

## Mechanism (main @ `68446b02`, `src/lib/workflow/worktree-manager.ts`)

1. `ensureWorktree` (~L842/901): behind by more than the threshold, no uncommitted changes, `!hasUnpushedCommits`, so it takes the "Safe to recreate" branch. Commits already pushed to the PR count as safe.
2. `removeStaleWorktree` (~L355/378) runs `git branch -D <branch>`.
3. Creation checks the branch with `show-ref --verify refs/heads/<branch>` (~L992), which is local only. The branch was just deleted, so it falls through to `git worktree add <path> -b <branch> <baseRef>` (~L1055): a new branch from base. `origin/<branch>` is never consulted.

## Impact

- QA reviews the wrong tree, and its verdict refers to code that isn't the PR.
- Any later commit on the recreated branch diverges from `origin/<branch>`. Pushing it is non-fast-forward, or a force-push overwrites the PR.
- It's latent in any repo where a PR's branch falls more than 5 commits behind base before a qa-only re-run, which is common on a busy default branch.

## Suggested fix

When `origin/<branch>` exists, recreate from it (`worktree add -B <branch> <path> origin/<branch>`) and then merge or rebase base in. Never `-b <branch> <base>` while a remote branch exists. A cheap guard: after any recreate, assert that `git rev-list --count <base>..HEAD` is greater than 0 when the issue has an open PR, and refuse or warn otherwise.

Reported from a graph-run session; mechanism traced by a sequant-repo session and re-checked against main.

## Acceptance Criteria

- [ ] AC-1: When `ensureWorktree` recreates a worktree and `origin/<branch>` exists, the recreated branch starts from `origin/<branch>`, so HEAD contains every commit `origin/<branch>` has. Evidence: a test with a temp repo whose PR branch is pushed and more than 5 commits behind base, asserting `git rev-list --count HEAD..origin/<branch>` is 0 after recreate, mutation-verified by restoring the `-b <branch> <baseRef>` path.
- [ ] AC-2: When `origin/<branch>` does not exist, recreate behaves as today (new branch from the base). Evidence: a test with an unpushed local-only branch.
- [ ] AC-3: A recreate that would leave HEAD with none of an existing `origin/<branch>`'s commits does not proceed silently: it refuses, or prints a warning in the same style as the existing "commits behind" line (`worktree-manager.ts:339`) and keeps the old worktree. Evidence: a test that forces the case and asserts the warning or refusal text.
- [ ] AC-4: The base the recreate path uses is the run's resolved base (`ResolvedRun.baseBranch`), or the spec records why it differs (graph doc OQ-2). Evidence: the spec comment's answer to OQ-2, and a test if the value is threaded through.
