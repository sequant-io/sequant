## Motivation

`sequant run` (including `sequant run --ready-gate`) records every run to `.sequant/metrics.json` via `RunOrchestrator.recordMetrics` → `MetricsWriter.recordRun`. Standalone `sequant ready <issue>` never has — this predates #915 and is not specific to it, but #915 surfaced it concretely: `sequant ready --escalate-effort --verbose` prints `effort: <base> → <escalated> (<phase> retry)` to stdout, but that escalation is never recorded anywhere durable. The same gap applies to `ready`'s other outcomes — `iterations`, `finalVerdict`, `tokensUsed`, `autoFixed` — all computed and returned by `runReadyGate` as a `ReadyResult`, all currently discarded once the CLI prints its report.

Practically: anyone using `sequant stats` or the dashboard to understand run behavior sees a complete picture for `sequant run` and a blind spot for standalone `sequant ready`. If `--ready-gate` usage and standalone `ready` usage diverge over time (e.g. teams that always gate manually rather than inline), that blind spot grows.

## Non-Goals

- Any edit under `plugin/`, `.claude/skills/` or `templates/skills/` (plugin freeze, I-1 of the graph doc).

- Not proposing `ready` inherit `run`'s exact `MetricRun` shape wholesale — a ready-gate pass isn't a `run` (no `phases: MetricPhase[]` in the same sense, no single `RunOutcome` that obviously maps from `ReadyTerminalReason`).
- Not proposing metrics become mandatory/blocking — should fail open like `run`'s own metrics recording does (best-effort, never fails the command).
- Not touching `run --ready-gate`'s existing recording path — that already works today (`IssueResult.readyGate.effortEscalations` → `RunOrchestrator.recordMetrics` → `MetricsWriter.recordRun`, added in #915).

## Design sketch (needs a decision, not prescribed here)

Two shapes worth weighing:

1. **Reuse `MetricRun` as-is.** Map `ReadyTerminalReason` → `RunOutcome` (e.g. `READY_FOR_MERGE`/`AC_MET` → `success`, everything else → `failure`), treat the gate's `qa`/`loop` dispatches as `phases`, `iterations` as `qaIterations` in the metrics sub-object. Reuses the existing schema and `sequant stats`/dashboard code with zero changes there, at the cost of a slightly awkward outcome mapping.
2. **A parallel, ready-scoped metric record.** A new schema entry (or a new top-level array) shaped around `ReadyResult` directly — `policy`, `reason`, `iterations`, `autoFixed.length`, `remaining.length`, `effortEscalations`, `tokensUsed`. Cleaner fit for the data, but needs its own `sequant stats`/dashboard support to be visible at all, and a second schema to maintain alongside `MetricRun`.

Whichever shape is chosen, wire it in `commands/ready.ts` right after `runReadyGate()` returns (same place the new `--verbose` escalation print already lives, added in #915), reusing the existing `MetricsWriter` — no new writer/storage layer needed.

## Acceptance Criteria

Decision (graph doc D-3, accepted by the owner on 2026-10-09): reuse `MetricRun` with a `source: "run" | "ready"` discriminator.

- [ ] AC-1: A standalone `sequant ready <issue>` run writes one `MetricRun` record with `source: "ready"` to `.sequant/metrics.json`, and a metrics write failure leaves the command's exit code unchanged. Evidence: a unit test on `commands/ready.ts` asserting `MetricsWriter.recordRun` is called with `source: "ready"` after `runReadyGate()` resolves, and a test where the writer throws and the exit code is unchanged.
- [ ] AC-2: The record carries policy, terminal reason mapped to an outcome, iteration count and `effortEscalations` in #915's shape. Evidence: the same unit test asserting those fields.
- [ ] AC-3: `sequant stats` shows standalone `ready` runs separately from `sequant run` runs. Evidence: a test on the stats aggregation with one record of each source, asserting two separate counts.
- [ ] AC-4: Records written before this change (no `source` field) read as `source: "run"`. Evidence: a test that loads a legacy metrics file.
- [ ] AC-5: `sequant run --ready-gate` metrics recording is unchanged. Evidence: the existing #915 tests pass unmodified.
