**Tier:** judgment   **Execution:** sequant_run

## Problem

When `git worktree add` exits non-zero, `ensureWorktree` logs "Failed to create worktree" and returns `null` (`src/lib/workflow/worktree-manager.ts:1153-1158`); `ensureWorktrees` drops the null and prints "N created, M reused" (:1296-1298); the issue's `worktree` is `undefined` in the orchestrator (`run-orchestrator.ts:1896-1908`); and `phase-executor.ts:1636` falls back to `cwd = process.cwd()`. **The issue's spec, exec and QA phases then run in the main checkout, on whatever branch is checked out there**, while a half-created worktree and branch sit on disk.

**Seen:** 2026-10-15, accretion-audit repo, two `sequant run` CLIs started 3 s apart. The loser logged `error: could not lock config file .git/config: File exists` / `error: unable to write upstream branch configuration` then `❌ Failed to create worktree: Preparing worktree (new branch ...)`, and continued. The exec committed and pushed to the feature branch because the prompt named the worktree path; the exec guard then ran `classifyExecChanges(main checkout)` (`phase-executor.ts:999`), whose `resolveBaseRef` found no recorded base for `main` and compared `origin/main..HEAD` = 0, so the run failed with "exec produced no changes (no commits, no uncommitted work)" against a branch that had the work. Recovery was `sequant run <n> --phases qa` on the reused worktree.

**Reproduced:** in a throwaway repo, 40 concurrent `git worktree add <path> -b <branch> origin/main` lost the `.git/config` lock 11 times (exit 255, branch created, no directory, not in `worktree list`, no upstream config). Each `worktree add -b` writes `branch.<name>.remote/merge` into the shared `.git/config`, so two CLIs in one repo race whenever their provisioning overlaps.

## Acceptance Criteria

- [ ] AC-1: Under worktree isolation, an issue whose worktree could not be created fails before any phase runs, with the captured git stderr in the issue result and the run log, and no phase for that issue has `cwd` equal to the main checkout. Evidence: `npx vitest run src/lib/workflow/run-orchestrator.worktree-failure.test.ts` → ≥ 2 passed, 0 failed (new file: a stubbed `ensureWorktrees` that omits one issue yields a failed issue result naming the stderr; `executePhase` is never called with `cwd === process.cwd()` for it); mutation-verified: restoring the `worktree?.path` fallback makes `src/lib/workflow/run-orchestrator.worktree-failure.test.ts > worktree provisioning > a missing worktree fails the issue before any phase` fail.
- [ ] AC-2: A `could not lock config file` failure from `git worktree add` is retried with short backoff, re-checking whether the branch now exists so the retry uses `worktree add <path> <branch>` instead of `-b`. Evidence: `npx vitest run src/lib/workflow/worktree-manager.integration.test.ts -t "config.lock"` → ≥ 2 passed, 0 failed (new file in the integration project, which has the 30 s timeout; real clone, a pre-created `.git/config.lock` released after the first attempt: the worktree is created on the retry; a lock never released ends in the AC-1 failure, not a hang).
- [ ] AC-3: `recordWorktreeBaseRef` (`phase-executor.ts:828`) uses the same retry and reports, rather than swallows, a final failure. Evidence: `npx vitest run src/lib/workflow/phase-executor.test.ts -t "recordWorktreeBaseRef"` → ≥ 2 passed, 0 failed.
- [ ] AC-4: Two concurrent runs in one repo both end with their worktrees created. Evidence: `npx vitest run src/lib/workflow/worktree-manager.integration.test.ts -t "concurrent"` → ≥ 1 passed, 0 failed (same new file; two `ensureWorktree` calls for different issues started together against one real clone both return non-null).

## Prior fixes / producers

- Prior fixes on this class: none for the lock race (`git log -S "could not lock" -- src` is empty; issue searches for "worktree add lock", "config file", "produced no changes" return nothing). #899 → #902, #1136 is the same class on the skill side (worktree created by the wrong party). Two fixes there, so this is a class: the ACs state the outcome (an issue never runs outside its worktree under isolation) rather than one call site.
- Producers of `.git/config` writes during provisioning: two, `git worktree add -b` (upstream config) and `recordWorktreeBaseRef` (`branch.<name>.sequantBase`), both racing across CLIs; the latter also swallows failure, which makes `--base <other>` runs silently compare against `origin/main`. No lock covers them: `LockManager` is per issue, `CheckoutLock` is used only by `sequant locks`, and both are no-ops under `SEQUANT_ORCHESTRATOR`.
