## Problem

119 catch clauses in non-test source have empty bodies; 25 are in `src/lib/workflow/batch-executor.ts`. Each is deliberate and commented ("State tracking errors shouldn't stop execution", "progress errors must not halt"), and the policy is right: a run should not die because a status write failed. What is missing is the other half of the rule. A dropped error leaves no debug line and no count, so when `.sequant/state.json` drifts it drifts invisibly, and `reconcile.ts` repairs symptoms whose cause was never recorded. #1469 was the same shape one layer down: a failed `git worktree add` was absorbed and the run continued in the main checkout; the fix added a failure side-channel so the caller could learn what happened.

Design: `src/lib/workflow/suppressed.ts` exports `noteSuppressed(scope: "state" | "progress" | "cleanup" | "platform" | "other", err: unknown, context?: string)`. It never throws, writes one debug line through the existing run-log debug path, and increments a per-run counter. `log-writer.ts` persists `suppressed: { total, byScope: Record<scope, number> }` as an **optional** field in `run-log-schema.ts` (the schema stays `version: 1`, as its own comments require for optional additions). Display in `sequant logs` is F-04, because `commands/logs.ts` is in #1471's scope.
