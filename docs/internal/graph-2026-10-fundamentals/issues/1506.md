## Problem

The fix-seam audit (59 merged fixes, 28 days) found the one seam tested through mocks is subprocess: 3 of 4 subprocess defects were tested by mocking `child_process`, and two logic fixes used hand-typed fixtures of `gh`'s output shape (#1229, #1214) — the failure "don't mock types you don't own" names: the fixture drifts, the test stays green, the code is wrong. 31 test files mock `child_process`; 6 of them fake `gh` inside the mock. `GitHubProvider` already owns 27 `gh` call sites, but 4 remain outside it: `batch-executor.ts` (`gh issue view --json title,labels` at :328 and `--json body,labels` at :388), `chain-preflight.ts` (`gh issue view --json body,state,title` at :207), `merge-check/report.ts` (`gh pr comment` at :314). All four are expressible through the existing `PlatformProvider` interface (`fetchIssue`, `postPRComment`).

Design: consumers take an optional `provider?: PlatformProvider` defaulting to `new GitHubProvider()` (D-D: no module-level test setter). `FakeGitHubProvider` implements the interface by replaying JSON fixtures under `src/lib/workflow/platforms/__fixtures__/gh/`, each produced by `scripts/capture-gh-fixtures.ts`, which runs the real `gh` and stamps `command`, `capturedAt`, `exitCode`, `stdout`, `stderr` (D-G). A fixture with `exitCode != 0` makes the fake throw the same error class `GitHubProvider` throws, so the `gh`-exit-status seam the audit flagged (#1319, #1320, #1464, #1268) is testable without `child_process`.
