## Problem

Across 15 recently completed issues the generated comments total 130k characters (spec comments 4.5k–14k each, QA reviews up to 9.6k). Every later phase and the owner re-read them. No skill or TS builder uses `<details>`. Layout is decided by whichever skill or function writes the comment, which is the prose-geometry defect #823 removed from the assess dashboard. §5 D-3.1 of the founding doc.

## Decisions

| ID | Decision | Rejected alternative |
|---|---|---|
| L-1 | One function, `renderIssueComment({kind, headline, acTable?, sections})`, renders headline, optional AC table, then every section inside a single `<details><summary>Details</summary>` block. Every line a parser anchors on (`QA_VERDICT`, the per-AC status rows #1525 reads, `SEQUANT_MUTATION`, assess markers) stays outside the block and keeps its current position | per-builder `<details>` sprinkled by hand |
| L-2 | `buildQaVerdictComment`, `merge-check/report.ts` and `review-residue.post.ts` call it | leaving the TS builders as they are and only changing skills |
| L-3 | Hidden `sequant comment render --kind spec\|qa --body-file -` reads a body whose first line is the headline and whose first markdown table is the AC table, and prints the laid-out comment; interactive skills pipe through it (#1606) | a prose instruction "wrap in details" in each skill |
