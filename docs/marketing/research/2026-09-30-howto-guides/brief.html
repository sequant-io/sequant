Research brief · 2026-09-30

How-to guides for Sequant: what to write, what to fix first

Three blind reads (a top-of-funnel visitor, a new user, an experienced user), a mine of 400 issues, 261 recorded runs and 180 Entire checkpoints, and a distribution scan. The result is a short list of fixes to make before any guide, then 12 guides ranked by who they help.

The reframe

The problem is the first ten humans, not converting downloads

840npm downloads, last 7 days
14unique GitHub page views, last 14 days
1referrer (Google, 1 visit)
0directories or awesome-lists that list Sequant

Downloads outnumber page views about 120 to 1. People don't install a tool they've never looked at, so the downloads are mirrors, bots and CI, the same pattern measured on 2026-09-13. The guides' job is to make the first ten people who arrive succeed on their first run and come back for a second. The target is ten humans who ran Sequant twice, not stars.

Stop-ship

Fix these before writing any guide

1. sequant init crashes for every interactive user (v2.18.0).

Inquirer 14 removed the list prompt type. Init calls it in all stack paths (src/commands/init.ts:811, :835, :854; src/lib/wizard.ts:267), so a real terminal gets UnknownPromptTypeError: Prompt type "list" is not registered. Reproduced locally against inquirer 14.2.2. The caret range came in with dependency bump #678 on 2026-05-30. Non-interactive and -y runs skip the prompt, which is likely why the tests stayed green. The fix is type: "select", plus one test that drives the interactive path.

2. The GitHub Action comment trigger lets anyone start a run.

sequant-action/examples/comment-trigger.yml and docs/features/github-actions-integration.md gate only on contains(comment.body, '@sequant run'). On a public repo, any commenter starts a run with write permissions and the owner's API key, on issue text the attacker wrote. Neither the action nor the example checks author_association. This is a security fix with its own issue, not a guide topic.

Blind reads

What each persona saw

Top-of-funnel visitor

"Would close the tab, maybe star."

Jargon stopped them before they saw any value: AC, worktree, quality gates, constitution. Version and permission warnings sit above Install. The most convincing fact, that second looks caught would-ship bugs, is two clicks deep.

Couldn't answer: cost per run, Pro/Max vs. API key, what the output looks like, how long it takes, how to write an issue.

New user

"Crashed at step one. A realistic first run is 20–40 minutes."

Blockers in order: the init crash; a GitHub remote nothing checks for; an issue with correctly formatted ACs and no example to copy; skills that must be committed; and slash commands that only work inside Claude Code, which the quickstart never says.

Wanted: "Your first issue", "Pick your install path", "Is this repo ready?"

Experienced user

"2 of 10 scenarios answered well, 1 not at all."

Worst served: the worktree gone after a merge, overlapping issues (the docs contradict themselves), vague ACs, and what to do after AC_NOT_MET. sequant abort is in no doc. Best served: prompt-injection hardening and halt/resume.

Wanted: recovery recipes, plus when-to-use guidance for batching, rigor levels, MCP and CI.

Evidence from history

What people actually do with Sequant

Caveat: this is almost all the maintainer's own usage, so frequency means "how often the maintainer did it", not how often outside users do. The non-Node adoption work (#1203) is the closest proxy for an outside user.

  • Re-running only QA after a fix is the second most common run: 74 of 261 runs, and barely documented. 24 issues hit AC_NOT_MET, and 20 of them still reached a PR, almost always through sequant run N --phases qa.
  • 53 of 58 issues in the log window reached a PR.
  • --chain succeeded on 28.6% of attempts vs. 80% for single issues. Guides should steer people away from it.
  • Quality loops pay off since 2.9/2.10. Issue graphs pay off for related work before a release and are ceremony for simple issues.
  • The MCP server has the most friction of any surface (39 issues). Nothing shows anyone using the GitHub Action.

Real walkthroughs to build guides on (all in the public repo)

  • Clean: #1199 → PR #1226. READY_FOR_MERGE, 4/4 ACs, about 25 minutes.
  • Failed and recovered: #1100 → PR #1102. Exec was killed at 30 minutes, AC_NOT_MET twice, then a QA-only re-run produced the PR.
  • Fixed by rewriting the AC, not the code: #1094 → PR #1128.

Voice

Writing rules for every guide

  1. Put the outcome in the first sentence: "You'll end with a PR that has a checked list of requirements."
  2. Then the command, before any explanation.
  3. Use plain words, with the term of art defined once: "requirement (Sequant calls these ACs)", "an isolated branch checkout (a worktree)".
  4. State cost and time with real measured numbers, or say they haven't been measured. Invented numbers sank trust in a comparable tool's Show HN thread.
  5. Every guide ends on a real public link: an issue, a PR, a QA comment.
  6. Mark behaviour by version ("since 2.18") so people on older installs aren't misled.
Screenshots

Screenshot strategy

Proof is what persuades people, and the current visuals don't show any. Every image should show something a reader can verify.

  • Terminal: VHS only, with a .tape committed next to the guide and re-rendered per release. vhs is installed, three tapes exist, and two have no committed GIF. No hand-taken PNGs; they go stale.
  • Proof shots: browser screenshots of a real issue's QA comment (requirements ✅/❌ with evidence) next to the PR at "checks green, awaiting your merge". Take them from a public example repo full of fictional issues so nothing private leaks, and link the live pages.
  • Hero GIF: replace the 9-second staged run with a real-time-labelled cut, e.g. "25 min, compressed", that ends on the PR and the checklist, not on "completed". sequant-demo-video already has render:gif, render:clip and thumbnail targets.
  • Rules: at most one hero image per guide, a still frame per step only where the output is hard to describe, and alt text that states what the image proves.
Distribution

Where these guides go

Check the plugin directory submission first.

Anthropic moved plugin submissions to claude.ai/directory/manage around 2026-09-28 and says the earlier Console form "is no longer supported". The 2026-08-30 submission probably went to the old form. Check platform.claude.com/plugins/submissions, then withdraw and resubmit, or email directory@anthropic.com.

  1. Lists people read: hesreallyhim/awesome-claude-code (54.9k stars; web form only, written by a human, no PRs), then jqueryscript's awesome-claude-code, buildwithclaude, claude-code-templates and the official MCP registry. These need a one-line description and a three-command quickstart.
  2. Guide 1 plus a new hero GIF. Together they meet the "demo GIF" precondition you set for HN.
  3. A research post with a reconciled number: rerun the 44% figure through the #1067 reconstruction before amplifying it. Post it on r/ClaudeCode as a text post from your personal account, on dev.to with #claudecode and the canonical URL on sequant.io, and in the Claude Discord.
  4. High-signal seeding: Anthropic's Project Showcase form, console.dev, Node Weekly, and a demo slot at a Claude Community meetup.
  5. Hold HN and Product Hunt until the GIF, 3 findings and users who can vouch exist. That's the existing decision, unchanged.

The comparable tools that took off (superpowers, ccpm) did it with a narrative post on the author's own site and then one big amplifier. Being listed in a directory alone did nothing: two listed issue-to-PR plugins have 0 and 2 stars.
