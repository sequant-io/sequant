### Code Review

**Strengths:**
- Follows the established `SEQUANT_SPEC`/`SEQUANT_PHASE` flat-JSON marker idiom precisely, including the `stripMarkdownCode()` fence-safety reuse — no reinvention.
- §6i's §7 wiring replicates §6h's exact 4-touchpoint shape (step-2 token, step-4 branch, both-mode checklist, both-mode template), which is what keeps `lint-skill-gates.ts`'s I1–I4 invariants passing.
- Genuinely dogfooded: the feature was applied to its own PR live during this QA pass (see Execution Verification), and the mutation-verification dogfood for AC-4 caught two *real* bugs during implementation (a floor-phrase wording mismatch that silently defeated the generic lint check, and a 3-way skill-mirror divergence from an interrupted restore) — both fixed and documented transparently in the PR body rather than hidden.
- `isGateTestEvidence`'s true-positive/true-negative unit tests use this issue's own real AC evidence text verbatim, not synthetic fixtures — satisfies the derived AC's intent precisely.

**Issues:**
- AC-3's literal text names a single function (`parseMutationMarkers`) as the thing that "rejects" bad markers; the implementation splits parsing and rejection across two functions. Flagged above — not blocking, but worth a maintainer's explicit sign-off since it's a plan-vs-ship divergence, however well-justified.
- `isGateTestEvidence` is a keyword heuristic (`fixture`/`section`/`flag`/`wired`/`exists`/`present`/`registered`/`mutation-verified`/`mutation test`) that could, in principle, misclassify a human-review-only AC whose evidence text happens to use one of these words (e.g. "reviewed manually, fixture exists in the demo env"). Not observed in the real backtest (7/18 rows in-scope, all genuinely gate-test-shaped), but it's a known false-positive surface, already named in the PR's own Pre-PR Confidence Check.

**Suggestions:**
- Consider renaming `parseMutationMarkers` in a follow-up to `parseMutationMarkersRaw` or similar if the split becomes a recurring point of confusion, or fold `classifyMutationMarker` calls into a single `parseAndClassifyMutationMarkers(prBody, diffTestFiles)` convenience wrapper — not required now, `/spec` already flagged and accepted the current shape.

- **Likely failure mode:** `isGateTestEvidence`'s keyword heuristic could over-fire on a future AC whose evidence text incidentally contains one of its trigger words (`fixture`/`section`/`flag`/`exists`/`present`) without actually being a CLAUDE.md-style gate test, sweeping it unnecessarily into the mutation-verification gate and demanding a marker that doesn't conceptually apply. Low current risk (measured 7/18 AC rows in the real backtest, all genuinely gate-test-shaped) but unbounded as the AC corpus grows.
- **Not tested:** `classifyMutationMarker`'s file-match is a simple filename/suffix check — it cannot detect a marker that names a real, unrelated test file (present in the diff for an unrelated reason) as if it were the mutation-covering test. This is explicitly out of scope per the issue's own Non-Goals ("no automated mutation-testing framework"), but worth naming as a residual gap for anyone relying on this gate as stronger proof than it is.
